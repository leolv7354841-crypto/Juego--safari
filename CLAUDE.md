# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Dead Zone" is a top-down 2D zombie survival game that runs in the browser (Chrome/Safari, desktop and phone). It is a static site: plain ES modules built with Vite (no framework). The only browser dependency is `@colyseus/sdk`, loaded lazily for online mode. All art and sound are generated in code (`js/render/sprites.js`, `js/ui/audio.js`). UI text, README and game copy are in Spanish; keep new player-facing text in Spanish.

## Commands

- Run locally: `npm run dev` (Vite dev server at http://localhost:8080). Opening `index.html` by double-click does not work because the modules need a server. `npm run build` writes `dist/`; `npm run preview` serves it (4173).
- No stamping: Vite hashes the output files. `js/core/version.js` exposes `VERSION` (injected at build, `dev` otherwise) and `hayVersionNueva()`, which compares it with `version.json` to show a "new version" toast.
- Publishing: a push to `main` (the default branch) deploys the Vercel project `deadzone` (`deadzone-five-red.vercel.app`). Vercel runs `npm run build` (`vite build` into `dist/`; `vercel.json` sets no-cache on `index.html`/`version.json` and immutable on `/assets/*`); static files that must keep their name (manifest, icons) go in `public/`. GitHub Actions: `ci.yml` checks Biome, the core tests, the Vite build, the server tests and Playwright; `servidor.yml` updates the Vultr VM over SSH (`deploy/actualizar.sh --esperar`) when `server/`, `js/` or `deploy/` change. The `yeyo.games` hub is a separate Vercel project (`yeyo-games`, Astro, deployed with the Vercel CLI, not in git) whose `vercel.json` rewrites `/deadzone/` to `deadzone-five-red.vercel.app`, so it always serves the latest production build.
- Browser game checks: `npm run lint` (Biome), `npm test` (node:test) and `npm run e2e` (builds, then Playwright against `vite preview`; override ports with `E2E_WEB_PORT`/`E2E_SERVER_PORT`).
- Production server: `wss://servidor.yeyo.games` (`NET.server`), a VM (Vultr, Mexico City, DNS at Hostinger) running `deploy/docker-compose.yml` (server + Caddy for `wss://`); setup and update steps in `deploy/README.md` (`deploy/instalar.sh`, `deploy/actualizar.sh`). `render.yaml` is the old free-tier option.
- Online server (`server/`, its own `package.json`): `npm run server:install` once, then `npm run server` (ws://localhost:2567, `/health`). `npm run server:test` runs the `node:test` suites (rooms, sim, netcode); `npm run build --prefix server` is a type-check only (`tsc --noEmit`). `npm run server:load` runs the load script (5 rooms × 4 bots by default; `--url`, `--origin`, `--rooms 5x4`) against a running server. The server runs `.ts` files directly with Node's type stripping (Node ≥ 22.18), so only erasable TypeScript syntax is allowed (no enums, decorators or parameter properties).

## Architecture

**Entry and loop.** `js/main.js` defines the `Game` class, which owns the state machine (`menu`, `play`, `pause`, `levelup`, `shop`, `over`, `account`, `board`, `coop`), the main loop, camera, HUD, shop rendering, and save/load. Most other modules are plain objects or classes that `Game` holds and calls into; they reach back to the game through a `game` argument (for example `Structures.explode(game, …)`, `Director.nextRound(game)`).

**Build and cache.** Vite bundles `js/main.js` from `index.html` and emits hashed files in `dist/assets/` (cached forever); `index.html` is never cached. `@colyseus/sdk` is a dynamic `import()` in `js/net/online.js` and becomes its own chunk. The server still imports `js/` directly, so modules must not depend on Vite-only features (`version.js` guards `__DZ_VERSION__` with `typeof`).

**Data and balance.** `js/core/config.js` holds all tuning: weapons, zombie stats, bounties, shop prices, drops, robot, rocket, golden zombie, Firebase `ONLINE` settings. Change numbers there rather than in the logic files.

**World.** `js/sim/world.js` builds a procedural city in chunks (`setChunkScale`, `maxChunks`), provides collisions (`pointBlocked`, `rectFree`), reachability checks, a flow field toward the player (`updateFlow`), and dynamic obstacles (`addDynamic`) that player-built structures register into.

**Horde and waves.** `js/sim/zombies.js` (`Horde`) runs all zombies: tactics (direct, flank, back-approach), a spatial grid (`horde.grid.query`) used by bullets, explosions, turrets and fire, and attacks. `js/sim/director.js` drives rounds: a queue of zombie types spawned at the screen edges, a `waiting`/`active` state, and the "next round" button. Golden zombie and spawn logic live in `main.js` (`spawnGolden`).

**Combat and structures.** `js/sim/player.js` (movement, stamina, weapons, reload, recoil), `js/sim/bullets.js` (segment-circle hit tests, piercing), `js/sim/build.js` (`Structures`: placement on a 20 px grid, stacking via `layer`, damage that targets the top piece, traps, grenades, molotov fires, rockets stuck to fat zombies, acid, turrets, explosions). `js/sim/robot.js` is a pilotable robot that absorbs hits while the player is on board; `main.js` routes its damage.

**Rendering.** `main.js` draws in world space with a camera that applies shake and kick; `js/render/lighting.js` handles darkness, flashlight and lamps; `js/render/particles.js` handles particles and ground decals; `js/sim/pickups.js` for ammo, medkits, and crates. `js/ui/input.js` unifies keyboard, mouse and touch (`input.mode === 'touch'` toggles the touch UI class on the root).

**Persistence and accounts.** `js/ui/accounts.js` manages accounts (name + 4-digit PIN), per-account localStorage keys (`saveKey()` for the rolling save, `checkKey()` for the checkpoint written at the end of each wave), and personal bests. Saves happen on a timer, at wave end, and on `pagehide`/`visibilitychange`. Dying deletes the run save but keeps the record. When the game runs as a Claude Artifact with a database, `accounts.js` also mirrors saves and scores to the cloud (`cloudSave`, `cloudPull`, `cloudClear`); outside Artifacts that path is inactive. The global leaderboard uses Firebase Realtime Database through its REST API; `ONLINE.url` in `js/core/config.js` must be set for it to work.

**Co-op (2 players).** `js/net/net.js` connects two phones with a 4-letter room code. It is pure P2P: all game traffic goes over two WebRTC data channels (`rel` reliable/ordered, `fast` unordered without retransmits; `stun` servers from `ICE`). Firebase `rooms/<code>` is only used for signaling (offer/answer SDP) and is deleted once the channels open; if they do not open within `OPEN_LIMIT`, joining fails with the `directa` error (there is no relay or TURN fallback). `js/net/coop.js` makes the host the simulation authority: the host runs the world and sends snapshots about 8–12 times per second; the guest renders them with prediction and sends inputs back. Code often branches on `coop.isHost`, `coop.isGuest`, `coop.active`, and `coopRun`. A guest's bullets are cosmetic; damage is computed on the host (see the guard in `hitZombie`). Preserve that split when adding combat features.

**Online mode (4 per room, 5 rooms, authoritative server).** `server/` is a Colyseus 0.18 server. `server/src/rooms/DeadZoneRoom.ts` owns the lobby (Schema state in `state.ts`: members, ready, owner, phase `waiting`/`loading`/`playing`/`finished`), capacity (`MAX_PLAYERS` per room, `MAX_ROOMS` rooms per process: `onCreate` throws `servidor-lleno`; idle lobbies close after `IDLE_ROOM_MINUTES`), origin and name checks in the static `onAuth` (runs at HTTP matchmaking, before a room is created), validation and rate limits (`validate.ts`), reconnection (`onDrop` → `allowReconnection`, same `sessionId`) and a fixed-step loop with bounded catch-up. `server/src/sim/ServerSim.ts` runs the real game modules headless (`shim.ts` fakes `document.createElement('canvas')`) for N players: it is the `game` object those modules see, sets `game.targets` (players) which `Horde.update` and `Pickups.update` use instead of `game.player`/`coop.peer`, records particles/sfx/decals as effects for nearby clients, and builds per-player snapshots. Clients send only intents (`'in'` with `[seq, mx, my, bits, angle, weapon]`); never trust client positions or hits. `js/net/online.js` is the client: lobby, fixed 60 Hz input with prediction/reconciliation of the local player (`Predictor` in `js/net/netcode.js`, which calls `Player.move`), interpolation of others and zombies (`Interp`), effect replay and diagnostics. `Player.update` is split into `move` (shared by server and prediction; keep it deterministic and input-only) and `act` (aim and weapons). Bullet-hit rules live in `js/sim/combat.js` and are used by both `main.js` and the server. `game.remoteSim` is true for a co-op guest or an online client: local bullets are cosmetic. The simulation tick rate is `NET.tickHz` in `js/core/config.js` and must match on both sides; other online tuning is in `NET` and in `server/.env.example`. Level-ups, the shop, building, throwables and the robot are server-authoritative online: each `Slot` in `ServerSim` has its own money, level/XP (XP is shared by the team, bounties go to the killer), pending upgrade choices (`choices`/`choiceN`, sent as `up` in the snapshot; offered mid-wave too, the client shows a `#btn-upgrade` button/U key instead of pausing), inventory `inv`, a `Robot`, and handlers `pick`/`shop` (shop only between waves). The heavy turret (`SHOP.heavy`) is mounted through the same `robot` act (`Structures.mountHeavy`/`leaveHeavy`); while `p.manned` is set, `Player.move` pins the player behind the cannon and `Player.act` fires the turret's ammo (`p.heavyAmmo`). The client sends `'pick'`/`'buy'` and `'act'` (`build`/`throw`/`robot`, tagged with the last input seq `s`; the server runs it when it reaches that input) and gets money in `st[7]`, acid and in-robot in `st[8..9]`, heavy-turret ammo and the manned turret's position in `st[10..12]`, other players' manned heavy turrets in `hv`, `ec`, `ps` (`STAT_KEYS`), `iv` (inventory in `SHOP_ORDER`), `rb` (robots), `gr`/`fi`/`so`/`bl` and, when they change, `blk`/`wir`/`sc` back. The server uses the real `Structures` (`build.js`), so code there must not assume a single `game.player` (use `game.targets` when set). While online, `online.update` runs even under the level-up/shop/pause screens: the world never pauses.

## Firebase rules for the online modes

The README contains the Realtime Database rules needed for the global leaderboard and co-op rooms. If you change the shape of `scores` or `rooms` writes in `accounts.js` or `net.js`, update the rules in the README to match.

## Conventions

- Plain ES modules with `import`/`export`; no transpilation. Browser APIs only.
- Comments and UI strings are in Spanish; the code is otherwise terse and written in the same style as the surrounding file.
- Keep rendering code in the module that owns the object (e.g. structure drawing in `build.js`), not in `main.js`.
