# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Dead Zone" is a top-down 2D zombie survival game that runs in the browser (Chrome/Safari, desktop and phone). It is a static site: plain ES modules built with Vite (no framework). `js/core`, `js/sim` and `js/net` are TypeScript (`.ts`, erasable syntax only); `js/render`, `js/ui` and the root files are JavaScript checked with `checkJs`. The only browser dependency is `@colyseus/sdk`, loaded lazily for online mode. All art and sound are generated in code (`js/render/sprites.js`, `js/ui/audio.js`). UI text, README and game copy are in Spanish; keep new player-facing text in Spanish.

## Commands

- Run locally: `npm run dev` (Vite dev server at http://localhost:8080). Opening `index.html` by double-click does not work because the modules need a server. `npm run build` writes `dist/`; `npm run preview` serves it (4173).
- No stamping: Vite hashes the output files. `js/core/version.ts` exposes `VERSION` (injected at build, `dev` otherwise) and `hayVersionNueva()`, which compares it with `version.json` to show a "new version" toast.
- Publishing: a push to `main` (the default branch) deploys the Vercel project `deadzone` (`deadzone-five-red.vercel.app`). Vercel runs `npm run build` (`vite build` into `dist/`; `vercel.json` sets no-cache on `index.html`/`version.json` and immutable on `/assets/*`); static files that must keep their name (manifest, icons) go in `public/`. GitHub Actions: `ci.yml` checks Biome, the core tests, the Vite build, the server tests and Playwright; `servidor.yml` updates the Vultr VM over SSH (`deploy/actualizar.sh --esperar`) when `server/`, `js/` or `deploy/` change. The `yeyo.games` hub is a separate Vercel project (`yeyo-games`, Astro, deployed with the Vercel CLI, not in git) whose `vercel.json` rewrites `/deadzone/` to `deadzone-five-red.vercel.app`, so it always serves the latest production build.
- Browser game checks: `npm run typecheck` (`tsc -p tsconfig.json` with checkJs plus `tsc -p tsconfig.strict.json`: `noImplicitAny` and `strictNullChecks` on core/sim/net), `npm run lint` (Biome), `npm test` (node:test) and `npm run e2e` (builds, then Playwright against `vite preview`; override ports with `E2E_WEB_PORT`/`E2E_SERVER_PORT`).
- Production server: `wss://servidor.yeyo.games` (`NET.server`), a VM (Vultr, Mexico City, DNS at Hostinger) running `deploy/docker-compose.yml` (server + Caddy for `wss://`); setup and update steps in `deploy/README.md` (`deploy/instalar.sh`, `deploy/actualizar.sh`). `render.yaml` is the old free-tier option.
- Online server (`server/`, its own `package.json`): `npm run server:install` once, then `npm run server` (ws://localhost:2567, `/health`). `npm run server:test` runs the `node:test` suites (rooms, sim, netcode); `npm run build --prefix server` is a type-check only (`tsc --noEmit`). `npm run server:load` runs the load script (5 rooms × 4 bots by default; `--url`, `--origin`, `--rooms 5x4`) against a running server. The server runs `.ts` files directly with Node's type stripping (Node ≥ 22.18), so only erasable TypeScript syntax is allowed (no enums, decorators or parameter properties).

## Architecture

**Layout of `js/`.** `core/` (config, util, version, shared types), `sim/` (game logic that also runs on the server: world, zombies, bullets, build, player, robot, pickups, director, combat, abilities, upgrades), `render/` (all drawing: sprites, lighting, particles and one `<x>.js` per sim module that has visuals), `net/` (client networking: `protocol.js` with the wire tables and `IN_*` bits shared with the server, `netcode.js`, `net.js`, `coop.js`, `online.js`) and `ui/` (input, audio, music, accounts, and one module per screen: `hud`, `shop`, `class`, `look`, `levelup`, `over`, `menu`, `account`, `board`, `lobby`, `icons`, `dom`). At the root: `main.js`, `states.js` (state table), `events.js` (combat events of the local player), `actions.js` (key/button actions), `save.js` (saved progress).

**Entry and loop.** `js/main.js` (about 300 lines) only coordinates: `Game` builds the modules, holds the run state (`money`, `kills`, `inv`, …), runs the loop and exposes, as one-line arrow fields, the `game.xxx(...)` methods that sim, net and e2e code call (`toast`, `killZombie`, `saveProgress`, `closeShop`, …). Everything else lives in modules of plain functions that take `game` as first argument (`openShop(game)`, `Structures.explode(game, …)`). `js/states.js` is the state machine as a table `STATES = { estado: { screen, music, enter, exit, update } }` (`menu`, `play`, `pause`, `levelup`, `shop`, `over`, `account`, `board`, `look`, `online`, `class`); use `setState(game, name)` and `stepState(game, dt)`, and add a new screen as a new entry. Each UI module in `js/ui/` has a `bindXxx(game)` that wires its own buttons (called from `Game.bindUi`). Adding a method to `Game` that a sim/net module calls means adding the arrow field in `main.js` (`test/estados.test.js` checks it against `GameHost` in `core/types.d.ts`).

**Build and cache.** Vite bundles `js/main.js` from `index.html` and emits hashed files in `dist/assets/` (cached forever); `index.html` is never cached. `@colyseus/sdk` is a dynamic `import()` in `js/net/online.ts` and becomes its own chunk. The server still imports `js/` directly, so modules must not depend on Vite-only features (`version.ts` guards `__DZ_VERSION__` with `typeof`).

**Data and balance.** `js/core/config.ts` holds all tuning: weapons, zombie stats, bounties, shop prices, drops, robot, rocket, golden zombie, Firebase `ONLINE` settings. Change numbers there rather than in the logic files.

**World.** `js/sim/world.ts` builds a procedural city in chunks (`setChunkScale`, `maxChunks`), provides collisions (`pointBlocked`, `rectFree`), reachability checks, a flow field toward the player (`updateFlow`), and dynamic obstacles (`addDynamic`) that player-built structures register into. `collide(e, r, passBlocks, ox, oy)` takes where the zombie ended the previous frame (`z.ox/z.oy`): if a push (crowd pressure, a bull's charge) moved its center into or across a wall, it goes back to the side it came from, never out the far side; whoever teleports a zombie clears `ox/oy` (the director with stragglers).

**Horde and waves.** `js/sim/zombies.ts` (`Horde`) runs all zombies: tactics (direct, flank, back-approach), a spatial grid (`horde.grid.query`) used by bullets, explosions, turrets and fire, and attacks. `js/sim/director.ts` drives rounds: a queue of zombie types spawned at the screen edges, a `waiting`/`active` state, and the "next round" button. Golden zombie and spawn logic live in `main.js` (`spawnGolden`).

**Combat and structures.** `js/sim/player.ts` (movement, stamina, weapons, reload, recoil), `js/sim/bullets.ts` (segment-circle hit tests, piercing), `js/sim/build.ts` (`Structures`: placement on a 20 px grid, stacking via `layer`, damage that targets the top piece, traps, grenades, molotov fires, rockets stuck to fat zombies, acid, turrets, explosions). `js/sim/robot.ts` is a pilotable robot that absorbs hits while the player is on board. `js/sim/rules.ts` holds the combat rules shared by `main.js` (through `js/events.js`) and `server/src/sim/ServerSim.ts`: `killZombie` (bounty, loot, golden zombie, fat acid), `hitZombie`, the golden-zombie clock, acid burn, rockets, robot hits and hit money loss; the caller passes hooks for what differs (whose money, who is notified). Change a combat rule there, not in both places. `js/sim/combo.ts` is the kill streak (`p.combo` on each `Player`, tuned by `COMBO` in config): whoever simulates (solo in `events.js`, `ServerSim` online) calls `comboKill` on a kill (its multiplier scales that kill's bounty and XP), `comboBreak` on a zombie hit and `comboTick` each step; the online client only receives it as `cb` (`applyCombo`) and the HUD draws it.

**Rendering.** `js/render/scene.js` draws each frame in world space with the camera of `js/render/camera.js` (shake and kick) and also resizes the canvas and adapts quality; `js/render/lighting.js` handles darkness, flashlight and lamps; `js/render/particles.js` handles particles and ground decals; `js/sim/pickups.ts` for ammo, medkits, and crates. `js/ui/input.js` unifies keyboard, mouse and touch (`input.mode === 'touch'` toggles the touch UI class on the root).

**Persistence and accounts.** `js/ui/accounts.js` manages accounts (name + 4-digit PIN), per-account localStorage keys (`saveKey()` for the rolling save, `checkKey()` for the checkpoint written at the end of each wave), and personal bests. Saves happen on a timer, at wave end, and on `pagehide`/`visibilitychange`. Dying deletes the run save but keeps the record. When the game runs as a Claude Artifact with a database, `accounts.js` also mirrors saves and scores to the cloud (`cloudSave`, `cloudPull`, `cloudClear`); outside Artifacts that path is inactive. The global leaderboard uses Firebase Realtime Database through its REST API; `ONLINE.url` in `js/core/config.ts` must be set for it to work.

**Modes, remote view and snapshots.** There are two game modes for the player: «Un jugador» and «En línea · 2 a 4» (a room of 2 to 4 people through the server; playing with a friend is creating a room and sharing the code or the `?sala=CODE` invite link). The old direct P2P co-op (WebRTC + Firebase signalling) no longer exists. `game.mode` (`js/net/mode.ts`) is one of `Solo` (also `detached`: a solo run that came out of an online room, never saved), `OnlineClient`, or `ServerMode` (what the shared sim modules see on the server). Ask it by intent, not identity: `authority()` (this device computes damage; false means local bullets are cosmetic), `inGroup()`, `savesProgress()` (only `Solo` that is not `detached`: progress saving belongs to «Un jugador» alone), `canBuild()`, `viaServer()`, and the request helpers `sendBuild/sendThrow/sendAbility/sendNextRound`. `resetRun()` always starts `Solo`; `online.ts` switches the mode when a room game starts and goes back to `Solo` `detached` when the player leaves. Do not add `coop.isHost`-style checks or `game.coop` (`test/llamadas.test.js` fails on them). `js/net/snapshot.ts` is the single encoder of the world part of a snapshot (`z zx zh o pl rb pk b gr fi so ms bl w ds tm`, plus `encodeStatic` for `blk wir sc`), used by `ServerSim.snapshot`, which adds the online fields (`me st wp ec ps iv ab hv up fx tt dg ml lft kl cb`). `js/net/remote.ts` (`game.remote`) decodes it for the online client: zombies and other players move with `Interp`, robots/pickups/bullets/structures/effects are applied the same way; `js/render/remote.js` draws peers and cosmetic bullets.

**Online mode (2 to 4 per room, 8 rooms, authoritative server).** `server/` is a Colyseus 0.18 server. `server/src/rooms/DeadZoneRoom.ts` owns the lobby (Schema state in `state.ts`: members, ready, owner, phase `waiting`/`loading`/`playing`/`finished`), capacity (`MIN_PLAYERS` = 2 connected members needed to start, `MAX_PLAYERS` = 4 per room, `MAX_ROOMS` = 8 rooms per process: `onCreate` throws `servidor-lleno`; idle lobbies close after `IDLE_ROOM_MINUTES`), origin and name checks in the static `onAuth` (runs at HTTP matchmaking, before a room is created), validation and rate limits (`validate.ts`), reconnection (`onDrop` → `allowReconnection`, same `sessionId`) and a fixed-step loop with bounded catch-up. `server/src/sim/ServerSim.ts` runs the real game modules headless (nothing under `js/core`, `js/sim` or `js/net/{protocol,netcode}` touches `document`, so no shim is needed) for N players: it is the `game` object those modules see, sets `game.targets` (players) which `Horde.update` and `Pickups.update` use instead of `game.player`, records particles/sfx/decals as effects for nearby clients, and builds per-player snapshots. Clients send only intents (`'in'` with `[seq, mx, my, bits, angle, weapon]`); never trust client positions or hits. `js/net/online.ts` is the client: lobby, fixed 60 Hz input with prediction/reconciliation of the local player (`Predictor` in `js/net/netcode.ts`, which calls `Player.move`), interpolation of others and zombies (`Interp`), effect replay and diagnostics. `Player.update` is split into `move` (shared by server and prediction; keep it deterministic and input-only) and `act` (aim and weapons). Bullet-hit rules live in `js/sim/combat.ts` and are used by both `main.js` and the server. `!game.mode.authority()` is true for an online client: local bullets are cosmetic. The simulation tick rate is `NET.tickHz` in `js/core/config.ts` and must match on both sides; other online tuning is in `NET` and in `server/.env.example`. Level-ups, the shop, building, throwables and the robot are server-authoritative online: each `Slot` in `ServerSim` has its own money, level/XP (XP is shared by the team, bounties go to the killer), pending upgrade choices (`choices`/`choiceN`, sent as `up` in the snapshot; offered mid-wave too, the client shows a `#btn-upgrade` button/U key instead of pausing), inventory `inv`, a `Robot`, and handlers `pick`/`shop` (shop only between waves). The heavy turret (`SHOP.heavy`) is mounted through the same `robot` act (`Structures.mountHeavy`/`leaveHeavy`); while `p.manned` is set, `Player.move` pins the player behind the cannon and `Player.act` fires the turret's ammo (`p.heavyAmmo`). The client sends `'pick'`/`'buy'` and `'act'` (`build`/`throw`/`robot`, tagged with the last input seq `s`; the server runs it when it reaches that input) and gets (besides the shared world part, `pl` now 19 numbers per player and `rb` 8 per robot) money in `st[7]`, acid and in-robot in `st[8..9]`, heavy-turret ammo and the manned turret's position in `st[10..12]`, other players' manned heavy turrets in `hv`, `ec`, `ps` (`STAT_KEYS`), `iv` (inventory in `SHOP_ORDER`), `rb` (robots), `gr`/`fi`/`so`/`bl` and, when they change, `blk`/`wir`/`sc` back. The server uses the real `Structures` (`build.js`), so code there must not assume a single `game.player` (use `game.targets` when set). While online, `online.update` runs even under the level-up/shop/pause screens: the world never pauses.

## Firebase rules

Firebase is only used for the global leaderboard (`scores`); online rooms do not touch it. The README contains the Realtime Database rules for it. If you change the shape of `scores` writes in `accounts.js`, update the rules in the README to match.

## Conventions

- Plain ES modules with `import`/`export`; Vite compiles the `.ts` modules and Node runs them with type stripping, so imports of those files use the `.ts` extension and only erasable syntax is allowed (no enums, decorators or parameter properties). Class fields assigned in the constructor are declared with `declare name: T;` (erased at runtime). Do not add `any`; shared shapes (`Cmd`, `Act`, `Snapshot`, `LobbyMember`) live in `js/core/types.d.ts` and the server imports them from there.
- Comments and UI strings are in Spanish; the code is otherwise terse and written in the same style as the surrounding file.
- Drawing lives in `js/render/<x>.js`, next to the logic module `js/sim/<x>.js` (e.g. `render/build.js` draws what `sim/build.js` simulates), never in the same file as the logic and not in `main.js` (the frame itself is `render/scene.js`). `js/core/` and `js/sim/` must load in Node without `document` and must not import `js/render/` or `js/ui/` (`test/carga.test.js` enforces it). World generation produces only data (`ops`, trees as seeds); `render/world.js` turns it into images.
